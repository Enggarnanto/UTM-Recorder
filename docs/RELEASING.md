# Publishing WordPress updates and repository layout

The updater targets the PUBLIC repository `Enggarnanto/UTM-Recorder`. It uses the native WordPress `Update URI` hook, checks GitHub's latest stable published Release, and accepts only matching installable ZIP assets from that repository. It does not download the repository's generated source archive or enable auto-update without the administrator's choice.

## Bootstrap

Install plugin 2.6.15 manually once per website. The updater cannot add itself to existing 2.6.14 installations remotely. Confirm the plugin folder is `utm-traffic-recorder` and the plugin file is `utm-traffic-recorder.php`. Then open **Traffic Recorder > Settings > Pembaruan plugin > Periksa pembaruan**.

If no public Release exists yet, the check reports that condition. A release equal to or older than the installed version produces no update button. The next higher stable release is shown by WordPress in Plugins. Publishing code to `main` without a Release does not offer an update.

## Automated release workflow (after these files are pushed)

1. Bump the PHP header, `UTR_VERSION`, stable tag, and current-version documentation. Keep WordPress 6.0+/PHP 7.4+ unless you also update the updater's advertised minimum requirements and test the change.
2. Update `docs/RELEASE-NOTES.md` for the final change.
3. Run PHP contract tests, `python -m unittest discover -s tests -p 'test_*.py'`, and the receiver test, then `python tools/build-release.py`. Inspect the versioned output under `dist/<version>/`.
4. Commit the source and push it to the repository. Review the code before tagging a production release.
5. Create and push tag `vX.Y.Z` matching the version header. The supplied `.github/workflows/release.yml` checks that equality, runs the tests, creates portable ZIPs, and publishes the Release with GitHub CLI. It runs only on version-tag pushes and uses the repository's scoped `GITHUB_TOKEN` for publishing.
6. Wait for the workflow to finish. Verify the Release includes `utm-traffic-recorder.zip` and the right version. Websites with the updater detect the higher release on a WordPress update check; use **Periksa pembaruan** to refresh the local GitHub cache immediately.

This workflow file is prepared locally; it does not run until committed/pushed and a matching tag is pushed. The production plugin ZIP and backend receiver ZIP are separate assets.

## Manual release alternative

Create a stable published GitHub Release, tag `vX.Y.Z`, and upload the built `utm-traffic-recorder.zip` as a Release asset. A versioned name `utm-traffic-recorder-X.Y.Z.zip` is also supported. Do not use GitHub's autogenerated **Source code (zip)**, because this repository contains more than the plugin folder. ZIP entries must use `/`, and the main file must be `utm-traffic-recorder/utm-traffic-recorder.php`.

GitHub API results are cached for six hours; temporary errors are cached for fifteen minutes. The manual check clears the cache and refreshes native WordPress update metadata. A hosting firewall or GitHub unauthenticated rate limit can temporarily delay checks. Existing source/asset checks reject prereleases, draft releases, arbitrary external download hosts, malformed tags, and unrelated plugin lookups.

The backend receiver and Apps Script code are not installed on external systems by a WordPress update. Apply changes to those receivers separately when their protocols change. Google Sheets and generic Webhook/API credentials remain separate and are never GitHub credentials.
